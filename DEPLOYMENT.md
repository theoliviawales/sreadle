# Sreadle Deployment Plan

How to take Sreadle (Sight Readle), a daily rhythm sight-reading game, from a
working prototype to a public website anyone can play every day.

## What we are deploying

Sreadle is a fully static, client-side web game:

- One self-contained `index.html` (inline CSS and JavaScript, no build step,
  no framework, no backend, no accounts, no database).
- The daily rhythm is computed in the browser from the date. Days 1 to 10 are
  hand-written rhythms; they live both in the page and as data files in
  `patterns/` (see "Patterns pipeline" below). Day 11 onward is generated by
  a seeded pseudo-random generator keyed to the puzzle number, so every
  player gets the same rhythm on the same day with no server involved.
- Player stats (streak, best scores) live in the player's own browser
  localStorage. Nothing is uploaded anywhere.

Because there is no server logic, deployment is just "put one HTML file on a
static host." Everything below follows from that.

## Live hosting: Cloudflare Pages

The game is live at **https://sreadle.fun**, hosted on Cloudflare
Pages (moved from GitHub Pages on November 2, 2026; the GitHub Pages copy
at `https://theoliviawales.github.io/sreadle/` still updates from the same
repository and works as a mirror).

1. **Repository**: `github.com/theoliviawales/sreadle`, public, `main`
   branch. The game ships as `index.html` at the repository root.
2. **Deploys are automated by Cloudflare's Git integration**: the Pages
   project `sreadle` is connected to the repository, and every push to
   `main` builds and deploys automatically (no build command, output
   directory `/`). The GitHub Actions workflow in `.github/workflows/ci.yml`
   is the quality gate only: it validates the patterns, checks that
   `patterns.json` is fresh, and runs the full test suite (128 tests).
3. **Verify**: open the URL on a phone and a desktop browser, play a full
   round, confirm audio starts after the first tap (mobile browsers require
   a user gesture for WebAudio), and confirm the displayed puzzle number
   matches the current date in America/Los_Angeles.
4. **Updates**: push to `main`; Cloudflare redeploys within about a minute.

Cost: $0. HTTPS is automatic. Uptime and bandwidth are more than sufficient
for a daily-game audience.

## Aggregate stats (live)

The game sends an anonymous beacon after a finished or abandoned round and
after a share, to `POST /api/stats`, served by the Pages Function in
`functions/api/stats.js`. The function stores only running counters per
puzzle day in the D1 database `sreadle-stats` (bound as `STATS` in
`wrangler.toml`): plays, completions, abandons, shares, attempt 1 versus 2,
and four accuracy bands. No IP addresses, user agents, cookies, timestamps,
or per-player records are stored, and the endpoint rejects anything outside
its allowlist. Read the totals any time at `GET /api/stats` or in the
Cloudflare dashboard under D1. The endpoint's validation and counter logic
is covered by unit tests (`tests/stats.test.mjs`); the live read path and
the database binding were verified at launch on November 2, 2026.

## Custom domain (optional, recommended once it has players)

1. Buy a domain, for example `sreadle.com` or `playsreadle.com`, from a
   registrar with free WHOIS privacy (Cloudflare Registrar or Porkbun are
   good defaults). Expect roughly $10 to $15 per year.
2. Point it at GitHub Pages: add the domain under Settings, then Pages, then
   Custom domain, and create the DNS records GitHub shows (four A records to
   GitHub Pages IPs for an apex domain, or one CNAME for `www`).
3. Enable "Enforce HTTPS" once the certificate provisions (usually under an
   hour).
4. Alternative: host on Cloudflare Pages instead and attach the domain there;
   Cloudflare gives faster global caching and privacy-friendly analytics in
   one dashboard. The same single file works unchanged.

## Admin page: creating new rhythms

The game ships with a built-in admin page (same `index.html`, reached only by
a private unlinked hash route that is not published here) designed for a
phone:

- Build a 4/4 measure element by element: duration chips (half, dotted
  quarter, quarter, dotted eighth, eighth, sixteenth), a Note/Rest toggle so
  any beat can be removed and turned into a rest, a Dot modifier, and a
  tuplet tool for groups of 3, 5, 6, and 7 in a beat, plus a Flam toggle for
  single notes: a flammed note is drawn with a small grace note just before
  it, and in the game it is played as two quick taps, the grace tap about
  0.11 seconds ahead of the main note, with both taps judged.
- A live beats counter (x / 4) and the game's own notation renderer show the
  measure as it is built; tapping a note in the preview flips it to a rest,
  dots it where the math stays valid, or deletes it. Measures can be added
  (up to 8), reordered by editing, and test-played through the real game
  before saving.
- Saved rhythms live in the browser's localStorage library ("My rhythms").
  Setting a day number on a saved rhythm makes that day use it on that
  device, overriding the generated rhythm locally.

### Publishing a created rhythm to all players

Static hosting has no database to save to, so publishing is a short pipeline
by design:

1. In the admin page, tap Export on the rhythm. This copies a compact JSON
   block (name, tempo, measures) to the clipboard. Save it to a file.
2. Publish it with one command (see "Patterns pipeline" below):
   `node scripts/publish-pattern.mjs exported.json 42` writes it as
   `patterns/day-042.json`, validates it, and regenerates `patterns.json`.
3. Commit and push. CI validates everything again and deploys, and the
   rhythm becomes that day's official puzzle for everyone.

Until step 3 happens, a created rhythm is private to the device that made
it. If self-serve publishing ever becomes important (for example, a second
admin or community submissions), that is the point to add the small backend
described under "If it outgrows static hosting": an authenticated endpoint
that accepts rhythm JSON and commits it, or a tiny database the page reads
at load. Neither is needed for a single admin working from one phone.

## Patterns pipeline

Authored rhythms are data, not code. The layout:

- `patterns/day-001.json` to `patterns/day-010.json`: one file per authored
  day, in the exact shape the admin creator exports (`name`, `bpm`,
  `measures`, plus the `day` it belongs to). Days 1 to 10 were extracted
  from the original hand-written table in `index.html` by
  `scripts/extract-days.mjs`, which uses the game's own notation decompiler,
  so the files and the page cannot drift apart in meaning.
- `patterns.json` (repository root): a single object mapping day number to
  rhythm, built from the files above. CI deploys it next to `index.html`;
  wiring the game to load authored days from it at runtime lands with the
  UX pass, after which the embedded table in `index.html` becomes only a
  fallback.
- `scripts/build-patterns.mjs`: validates every pattern file and writes
  `patterns.json`. Validation mirrors the game's own rules: each measure
  sums to exactly 4 beats, tempo between 30 and 200 BPM, at most 8 measures,
  tuplet sizes limited to 3, 5, 6, and 7 with one cell per member, and flams
  only on single notes. A bad file fails the build with the day and measure
  named.
- `scripts/publish-pattern.mjs`: the one-command publishing path described
  above.

Editing a day by hand is equally supported: edit its JSON in `patterns/`,
run `node scripts/build-patterns.mjs`, commit both the day file and the
regenerated `patterns.json`, and push.

## Tests and CI

Run the tests locally with:

```sh
npm test
```

The suite uses only the Node test runner (no dependencies to install) and
checks the real shipped files: every authored measure sums to exactly 4
beats with no gaps in the compiled chart, the Day 12+ generator is
deterministic across fresh runs (sampled at days 12, 50, and 365), the flam
rules hold (authored days may carry the owner's flams, Day 10 is capped at
2, and generated days have at most 1), and every pattern file round-trips through the validator
and the game's own sanitizer.

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull
request: it rebuilds `patterns.json` and fails if the committed copy is out
of date, then runs `npm test`. On pushes to `main`, after the tests pass,
it deploys to Cloudflare Pages as described above; when the Cloudflare
secrets are absent the deploy step says so in the log and skips, without
failing the run.

## Make it feel like a real daily game

- **Midnight rollover**: the puzzle number is derived from the date in
  America/Los_Angeles, so a new Sreadle appears at midnight Pacific for
  everyone. This is a deliberate choice (it is the home timezone); document it
  on the page so players are not surprised.
- **Share results**: the results screen's Share button (native share sheet on
  phones, clipboard fallback) produces Wordle-style text: puzzle number,
  accuracy, score, best combo, which attempt it was, per-measure
  green/yellow/red squares, and a deep link to that exact puzzle,
  `https://sreadle.fun/?day=N`. The page reads the
  `?day=N` parameter on load and opens that puzzle directly. Add Open Graph
  meta tags and a 1200x630 share image so links pasted into chats and social
  apps unfurl with a title and picture.
- **Attempts**: each daily puzzle allows exactly 2 attempts per player,
  stored per puzzle in localStorage; after the second attempt the puzzle
  locks and shows the player's best result. Attempts are a client-side
  honor-system rule (a determined player can clear site data), which matches
  how Wordle-style games treat their limits; only a backend with accounts
  could enforce it harder, and that is deliberately out of scope.
- **Add to home screen**: add a web app manifest and an icon so the site
  installs like an app on phones. No app store, no review process.
- **Analytics (privacy-friendly)**: Cloudflare Web Analytics or Plausible, a
  single script tag, no cookies, just daily player counts and referrers.
  GitHub Pages itself provides no visitor stats.

## Quality checklist before announcing it

- Play Days 1 to 11 and a few generated days (12+) on a real phone; confirm
  every measure sums to exactly 4 beats and generated days are identical
  across two different browsers (determinism check).
- Test in Safari iOS and Chrome Android: audio unlock, tap latency, layout in
  portrait, no double-tap zoom during play.
- Check the results/share text on a phone and paste it into a message to
  confirm formatting survives.
- Confirm the page works fully offline after first load is NOT required, but
  nothing on the page should depend on external fonts or CDNs being up.

## If it outgrows static hosting (future options, not needed now)

- **Accounts and cross-device streaks**: add a small backend (Supabase or
  Firebase) for sign-in and synced stats. This is the only feature that truly
  needs a server.
- **Leaderboards**: same backend, one table of daily scores; add anti-cheat
  sanity checks (max plausible score per puzzle) before trusting submissions.
- **Hand-authored seasons**: done for Days 1 to 10. The `patterns/` pipeline
  above is how new hand-written days ship; authored days beat generated
  ones, still static, still free.
- **Native apps**: wrap the same page with Capacitor for the iOS/Android
  stores. Only worth it for push notifications ("today's Sreadle is ready"),
  which a website cannot send reliably on iOS.
